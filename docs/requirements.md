# Test Agent — 项目需求文档

---

## 1. 项目概述

### 1.1 项目名称

**Test Agent** — 基于 LLM 的智能路由器测试 Agent

### 1.2 项目定位

Test Agent 是一个针对华为 NE 高端路由器设计的 **高权限自主 Agent 系统**
，它能够理解用户的自然语言测试指令（如测试用例），并结合附加的专业领域知识文档，自主规划测试步骤，对复杂组网拓扑中的路由器设备进行自由配置和测试验证，并将配置结果实时反馈给用户，最终让用户得到一套配置好的、满足特定测试需求的组网拓扑。

简而言之：**用户用自然语言描述测试需求，Agent 自动完成路由器配置和验证。**

### 1.3 核心价值

| 传统方式      | Test Agent 方式     |
|-----------|-------------------|
| 手动逐台登录设备  | Agent 自动操作多台设备    |
| 手动编写测试配置  | 自然语言描述需求即可        |
| 人工判断测试结果  | Agent 自动验证并报告     |
| 重复性测试耗时耗力 | Agent 自动执行，人工只需审核 |

### 1.4 项目边界

**本项目关注（In Scope）**：

- Agent 核心推理-行动循环
- 路由器设备配置下发与查询
- 测试结果验证
- 多设备协调操作+
- Web 交互界面
- LLM 模型切换

**本项目不关注（Out of Scope）**：

- 过度安全设计（路由器暴露的命令已经足够安全，不会出现rm -rf的极度危险命令，只需对极少数命令进行警告即可）
- 用户权限管理（RBAC 角色体系）
- 计费与 Token 用量限制
- 自动化测试用例管理系统

## 3. 业务场景详细描述

### 场景 1：单设备基础配置

**用户故事**: 我需要在指定路由器上配置 OSPF，以便验证路由协议基本功能。

**对话示例**:

```
用户: 请在 R1 上配置 OSPF，进程号 1，area 0，宣告 10.1.1.0/24 和 192.168.1.0/24 两个网段

Agent: 我来帮你在 R1 上配置 OSPF。

首先查看 R1 当前的 OSPF 配置：
┌─ DeviceTool [R1] ─────────────────┐
│ > display ospf brief              │
│ (No OSPF Process)                 │
└───────────────────────────────────┘

当前没有 OSPF 配置，开始下发新配置：
┌─ DeviceTool [R1] ───────────────-──┐
│ > system-view                      │
│ > ospf 1                           │
│ > area 0                           │
│ > network 10.1.1.0 0.0.0.255       │
│ > network 192.168.1.0 0.0.0.255    │
│ > return                           │
│ Configure Success!                 │
└────────────────────────────────────┘

验证配置是否生效：
┌─ DeviceTool [R1] ─────────────────┐
│ > display ospf brief              │
│ OSPF Process 1 with Router ID     │
│ Area 0: 2 networks                │
└───────────────────────────────────┘

✅ OSPF 配置完成。进程号 1，Area 0 下已宣告 2 个网段。
```

### 场景 2：多设备端到端测试

**用户故事**: 作为一名高级测试工程师，我需要在 R1 和 R2 之间建立 OSPF 邻居关系并验证邻居状态达到 Full。

**对话示例**:

```
用户: 在 R1 和 R2 之间配置 OSPF 邻居，area 0，验证邻居建立成功

Agent: 收到。我将：
1. 查询 R1-R2 的互联拓扑信息
2. 分别在两台设备上配置 OSPF
3. 等待收敛后验证邻居状态

步骤 1/3：获取当前拓扑
┌─ TopologyTool ─────────────────────┐
│ R1 GE0/0/1 (10.1.1.1/30)           │
│   ↕                                │
│ R2 GE0/0/1 (10.1.1.2/30)           │
└────────────────────────────────────┘

步骤 2/3：配置 OSPF（两台设备并行）
┌─ DeviceTool [R1] ─────┐  ┌─ DeviceTool [R2] ─────┐
│ ospf 1                │  │ ospf 1                │
│  area 0               │  │  area 0               │
│   network 10.1.1.0    │  │   network 10.1.1.0    │
│           0.0.0.3     │  │           0.0.0.3     │
│ ✅ 配置成功           │  │ ✅ 配置成功           │
└───────────────────────┘  └───────────────────────┘

步骤 3/3：验证邻居状态
┌─ VerifyTool [R1] ──────────────────┐
│ > display ospf peer brief          │
│ Assert: contains "Full"            │
│ Retry: 1/3 → Pass                  │
│                                    │
│ Area 0:                            │
│ Router ID    State  Interface      │
│ 10.1.1.2     Full   GE0/0/1        │
└────────────────────────────────────┘

✅ 测试通过。R1-R2 OSPF 邻居已建立，状态为 Full。
```

### 场景 3：故障排查

**用户故事**: 测试过程中 OSPF 邻居起不来，我需要 Agent 帮我排查原因。

```
用户: R1 和 R2 的 OSPF 邻居一直建不起来，帮我查查原因

Agent: 我来逐步排查 OSPF 邻居无法建立的可能原因。

排查项 1/5：接口状态
┌─ DeviceTool [R1] ──────────────────┐
│ > display interface GE0/0/1        │
│ Physical: UP  Protocol: UP         │
│ ✅ Interface 状态正常              │
└────────────────────────────────────┘

排查项 2/5：IP 连通性
┌─ DeviceTool [R1] ──────────────────┐
│ > ping 10.1.1.2                    │
│ 5 packets sent, 5 received, 0% loss│
│ ✅ IP 连通正常                     │
└────────────────────────────────────┘

排查项 3/5：OSPF 配置一致性
┌─ DeviceTool [R1] ───────┐  ┌─ DeviceTool [R2] ───────┐
│ > display ospf          │  │ > display ospf          │
│ Area: 0                 │  │ Area: 1                 │
│ Hello: 10s              │  │ Hello: 10s              │
│ Dead: 40s               │  │ Dead: 40s               │
└─────────────────────────┘  └─────────────────────────┘

⚠️ 发现问题：R1 属于 Area 0，R2 属于 Area 1，Area 不一致！
OSPF 邻居要求互联接口的 Area ID 必须相同。

建议修复：将 R2 的 OSPF 接口改为 Area 0。是否需要我执行修复？
```

### 场景 4：配置回滚

```
用户: 刚才在 R1 上配了 OSPF 但是参数不对，帮我回滚掉

Agent: 我先查看 R1 当前的 OSPF 配置，然后清除它。
┌─ DeviceTool [R1] ──────────────────┐
│ > display current-configuration    │
│   section ospf                     │
│ ospf 1                             │
│  area 0                            │
│   network 10.1.1.0 0.0.0.255       │
│   network 192.168.1.0 0.0.0.255    │
└────────────────────────────────────┘

┌─ DeviceTool [R1] ──────────────────┐
│ > system-view                      │
│ > undo ospf 1                      │
│ Delete Success!                    │
│ > return                           │
└────────────────────────────────────┘

✅ 已回滚，R1 上的 OSPF 进程 1 已完全删除。
```

### 场景 5：批量验证

```
用户: 帮我检查所有设备的 OSPF 邻居是否都是 Full 状态

Agent: 我将逐个检查拓扑中所有设备的 OSPF 邻居状态。

┌─ VerifyTool [R1] ──────┐  ┌─ VerifyTool [R2] ──────┐
│ Peer 10.1.1.2  Full    │  │ Peer 10.1.1.1  Full    │
│ Peer 10.1.2.2  Full    │  │ Peer 10.1.3.2  Full    │
└────────────────────────┘  └────────────────────────┘

┌─ VerifyTool [R3] ──────┐
│ Peer 10.1.2.1  Full    │
│ Peer 10.1.3.1  Full    │
└────────────────────────┘

✅ 全部通过。3 台设备共 6 个 OSPF 邻居，状态均为 Full。
```

## 4. 功能需求

### 4.1 需求分级

- **P0（核心）**: 没有这些功能系统无法工作
- **P1（重要）**: 显著提升使用体验，计划在首个版本实现
- **P2（期望）**: 有价值但可延后，计划在后续版本实现

### 4.2 P0 — 核心功能

#### F-001：Agent 对话引擎

| 字段           | 内容                                                                                    |
|--------------|---------------------------------------------------------------------------------------|
| **描述**       | 用户通过自然语言与 Agent 进行多轮对话，Agent 自主规划并执行测试操作                                              |
| **验收标准**     | 1. 用户发送消息后，Agent 能理解意图并调用工具<br/>2. 支持多轮对话，Agent 记住上下文<br/>3. Agent 在工具执行后能根据结果继续推理    |
| **技术方案**     | LangGraph 状态图实现 ReAct 循环                                                              |
| **Agent 权限** | Agent 对当前拓扑内**所有设备**拥有完整操作权限，不限于用户明确提及的设备；P0 阶段包括重启设备在内的所有操作无需人工审批（审批机制为 P2 功能）       |
| **执行限制**     | 单次任务最大步骤数（`max_iterations`）默认值为 **30**，可通过前端对话参数或服务器配置文件覆盖；达到上限后 Agent 停止执行并向用户报告当前进度 |

**Agent 终止条件层级**（参考 Claude Code 实现，按检查优先级排列）：

| 优先级   | 终止原因                  | 检查时机                | 说明                                        |
|-------|-----------------------|---------------------|-------------------------------------------|
| 🔴 最高 | `context_overflow`    | 每轮循环开始前、LLM 调用前     | Token 用量超出上下文窗口硬限制，所有压缩策略已耗尽              |
| 🔴 高  | `user_abort`          | LLM 流式输出期间 / 工具执行期间 | 用户手动取消当前执行（WebSocket 取消信号）；中断后需清理未完成的工具调用 |
| 🔴 高  | `api_error`           | LLM 调用异常捕获          | LLM API 不可用或返回异常，重试 3 次后终止                |
| 🟡 中  | `max_turns`           | 工具执行完毕后、进入下一轮前      | 达到 `max_iterations` 上限                    |
| 🟢 正常 | `completed`           | LLM 响应解析后           | LLM 未发起工具调用，表示任务已完成——这是最正常的终止路径           |
| 🟢 正常 | `diminishing_returns` | 工具执行完毕后（P2 实现）      | 连续 3 次循环中 Token 增量低于阈值，判定为低效重复，自动停止       |

**终止后的用户反馈**：每种终止原因通过 `agent_done` WebSocket 消息携带独立的 `reason` 字段返回前端，前端根据不同原因展示对应的 UI 提示（如正常完成 vs
达到上限 vs 出错）。

#### F-002：设备命令执行

| 字段       | 内容                                                        |
|----------|-----------------------------------------------------------|
| **描述**   | Agent 能够在指定路由器上执行 CLI 命令并获取输出                             |
| **验收标准** | 1. 支持查询命令<br/>2. 支持配置命令<br/>3. 命令执行有超时保护<br/>4. 返回完整的命令输出 |
| **技术方案** | DeviceTool，底层通过 SSH 连接设备                                  |

#### F-003：拓扑感知

| 字段       | 内容                                                                                                                                                                                           |
|----------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **描述**   | Agent 能够查询当前测试拓扑的设备列表、互联关系、IP 地址等信息                                                                                                                                                          |
| **验收标准** | 1. 能查询拓扑中所有设备<br/>2. 能查询任意两台设备的互联接口和 IP<br/>3. 拓扑精简摘要自动注入 System Prompt；详细信息可通过 TopologyTool 按需查询                                                                                            |
| **技术方案** | **双轨策略**：① System Prompt 全量注入——会话开始时将拓扑精简摘要（设备名、管理IP、互联关系表）注入系统提示词，使 Agent 在推理阶段即有全局视野；② TopologyTool 按需查询——提供细粒度接口（如单台设备的接口详情），Agent 在需要精确数据时主动调用。考虑到拓扑规模一般不超过 10 台设备，全量注入在 context 占用上可接受。 |

#### F-004：LLM 模型切换

| 字段       | 内容                                                           |
|----------|--------------------------------------------------------------|
| **描述**   | 支持在内部部署的 LLM 和外部 API 之间一键切换                                  |
| **验收标准** | 1. 修改配置即可切换模型<br/>2. 切换后新对话使用新模型<br/>3. 至少支持：部门内部 LLM、智谱 GLM |
| **技术方案** | LLMProvider 抽象接口 + Factory 模式                                |

#### F-005：Web 对话界面

| 字段       | 内容                                                                         |
|----------|----------------------------------------------------------------------------|
| **描述**   | 提供基于浏览器的对话界面，用户通过 Web 页面与 Agent 交互                                         |
| **注意**   | 页面应该可以直接注入部门当前已有web页面（似乎使用`<iframe>`标签即可）                                  |
| **验收标准** | 1. 用户在浏览器中输入消息并发送<br/>2. Agent 的回复和工具执行结果实时流式展示<br/>3. 工具调用有明确的视觉区分（卡片式展示） |
| **技术方案** | FastAPI WebSocket + Vue 3 前端                                               |

### 4.3 P1 — 重要功能

#### F-006：断言验证

| 字段       | 内容                                                                                       |

#### F-007：多设备并行操作

| 字段       | 内容                                                       |
|----------|----------------------------------------------------------|
| **描述**   | Agent 能够同时在多台设备上执行操作，提升测试效率                              |
| **验收标准** | 1. 不同设备的命令可以并行执行<br/>2. 并行结果正确归属到各设备<br/>3. 单台设备上的命令仍然串行 |
| **技术方案** | LangGraph 并行节点 / DeviceTool 声明 `is_concurrent_safe=True` |

#### F-008：会话管理

| 字段       | 内容                                                           |
|----------|--------------------------------------------------------------|
| **描述**   | 支持多用户同时使用，每个用户有独立的对话历史                                       |
| **验收标准** | 1. 不同用户的对话互相隔离<br/>2. 用户可以查看自己的历史会话<br/>3. 用户可以创建新会话 / 继续旧会话 |
| **技术方案** | SessionManager + LangGraph thread_id + 数据库持久化                |

#### F-009：会话持久化与恢复

| 字段       | 内容                                                                |
|----------|-------------------------------------------------------------------|
| **描述**   | Agent 的对话状态自动保存，即使对话中断、服务重启也能恢复                                   |
| **验收标准** | 1. 每轮工具调用后自动保存检查点<br/>2. 中断后用户可以继续之前的对话<br/>3. 长时间测试（30分钟+）不会丢失进度 |
| **技术方案** | LangGraph Checkpointer (SQLite)                                   |

## 5. 拓扑定义规范

测试拓扑数据存储在数据库中，通过 Web 界面进行 CRUD 管理。开发阶段可使用 YAML 种子文件（存放在 `backend/seeds/` 目录下）导入初始数据。

### 5.1 拓扑数据格式

以下为种子数据的 YAML 格式示例（用于开发阶段导入数据库），生产环境通过 Web 界面管理：

```yaml
# backend/seeds/ospf_basic.yaml
name: "OSPF 基础测试拓扑"
description: "3 台路由器组成的三角形拓扑，用于 OSPF 基础功能测试"
version: "1.0"

# 设备定义
devices:
  - name: R1
    type: router              # router / switch / firewall
    vendor: huawei            # huawei / cisco / ...
    model: NE40E              # 设备型号
    management:
      protocol: ssh           # ssh / telnet / netconf
      host: 10.10.10.1
      port: 22
      username: admin
      password: "${R1_PASSWORD}"  # 支持环境变量引用

  - name: R2
    type: router
    vendor: huawei
    model: NE40E
    management:
      protocol: ssh
      host: 10.10.10.2
      port: 22
      username: admin
      password: "${R2_PASSWORD}"

  - name: R3
    type: router
    vendor: huawei
    model: NE40E
    management:
      protocol: ssh
      host: 10.10.10.3
      port: 22
      username: admin
      password: "${R3_PASSWORD}"

# 互联关系
links:
  - endpoints:
      - device: R1
        interface: GE0/0/1
        ip: 10.1.1.1/30
      - device: R2
        interface: GE0/0/1
        ip: 10.1.1.2/30
    description: "R1-R2 互联"

  - endpoints:
      - device: R1
        interface: GE0/0/2
        ip: 10.1.2.1/30
      - device: R3
        interface: GE0/0/1
        ip: 10.1.2.2/30
    description: "R1-R3 互联"

  - endpoints:
      - device: R2
        interface: GE0/0/2
        ip: 10.1.3.1/30
```

### 6.4 前后端通信协议

前后端采用 **REST API + WebSocket 混合**通信方式，按职责分工如下：

| 通信方式          | 适用场景        | 示例                             |
|---------------|-------------|--------------------------------|
| **REST API**  | 无状态 CRUD 操作 | 拓扑管理、会话列表查询、模型配置、用户信息          |
| **WebSocket** | 实时双向流式通信    | 对话消息收发、Agent 推理过程流式输出、工具调用实时展示 |

#### WebSocket 消息类型定义

所有 WebSocket 消息采用统一 JSON 结构：`{ "type": "<消息类型>", "data": { ... } }`

| 消息类型               | 方向        | 说明                                                             |
|--------------------|-----------|----------------------------------------------------------------|
| `user_message`     | 客户端 → 服务端 | 用户输入的文本消息，可携带 `max_iterations` 等会话参数                           |
| `agent_text_delta` | 服务端 → 客户端 | Agent 文本回复的流式片段（streaming token）                               |
| `tool_call_start`  | 服务端 → 客户端 | 工具调用开始，包含工具名和入参                                                |
| `tool_call_result` | 服务端 → 客户端 | 工具调用结果，包含输出内容和耗时                                               |
| `agent_done`       | 服务端 → 客户端 | 本轮 Agent 执行结束，携带终止原因（`completed` / `max_iterations` / `error`） |
| `error`            | 服务端 → 客户端 | 错误通知，包含错误码和用户可读的错误描述                                           |

### 7.4 上下文窗口管理

> 参考实现：Claude Code 的多层上下文管理策略（详见 `reference/02-context-management.md`）

随着多轮对话的进行，对话历史（尤其是设备命令输出）会快速累积并可能超出 LLM 的上下文窗口。系统需采用**三层递进压缩策略**：

| 层次     | 策略名称                | 触发条件                   | 机制                                                                                          | 优先级     |
|--------|---------------------|------------------------|---------------------------------------------------------------------------------------------|---------|
| **L1** | 微压缩 (Micro Compact) | Token 用量达到警戒阈值         | 扫描历史消息，将冗长的设备命令输出（如 `display current-configuration`）替换为摘要占位符 `[命令输出已清理，共 N 行]`，保留最近 K 条完整结果 | 最优先，成本低 |
| **L2** | 全量总结 (Auto Compact) | L1 不足以释放空间，Token 逼近硬限制 | 调用 LLM 将整段对话历史压缩为结构化摘要，然后**硬重注入关键状态**（见下文）                                                  | 次优先，准确  |
| **L3** | 硬截断 (Drop Head)     | L2 失败（如总结请求本身超长）       | 直接丢弃最早的 N 轮对话，保留 System Prompt + 最近的对话                                                      | 兜底保护    |

**Token 阈值设计**（以 200K context window 为例）：

```
有效窗口 = API 上下文限制 - LLM 输出预留 (20K)
├── 正常运行区  .... [0, 有效窗口 - 20K)
├── 警戒区域    .... [有效窗口 - 20K, 有效窗口 - 5K)   → 触发 L1 微压缩
├── 危险区域    .... [有效窗口 - 5K, 有效窗口)          → 触发 L2 全量总结
└── 硬阻塞     .... ≥ 有效窗口                        → 触发 L3 / 终止循环
```

**关键机制 — 状态外置与重注入**：

上下文压缩后，不能依赖 LLM 在自我总结中记住所有关键状态。系统应维护一个结构化的 `AgentContextState`，在压缩完成后将以下信息以系统消息形式**硬编码重注入**
新的上下文：

- 当前拓扑摘要（设备列表、互联关系）
- 当前设备连接状态
- 用户的原始任务目标
- 已完成的步骤和未完成的待办事项

## 11. 术语表

| 术语                      | 定义                                                 |
|-------------------------|----------------------------------------------------|
| **ReAct 循环**            | Reasoning + Acting，Agent 的「思考 → 行动 → 观察」交替模式       |
| **max_iterations**      | Agent 单次任务的最大步骤数上限，防止无限循环；默认 30，可配置                |
| **Checkpointer**        | LangGraph 的状态快照机制，用于会话持久化与断点恢复                     |
| **Tool**                | Agent 可调用的外部能力（函数），如 DeviceTool、TopologyTool       |
| **System Prompt**       | 每次请求时注入给 LLM 的系统级提示词，包含拓扑摘要、角色定义等                  |
| **MCP**                 | Model Context Protocol，用于集成外部工具服务器的标准协议            |
| **thread_id**           | LangGraph 用于标识一个独立对话线程的 ID，对应一个用户会话                |
| **Micro Compact**       | 微压缩策略，优先清理冗长的工具输出以释放上下文空间，成本低                      |
| **Auto Compact**        | 全量压缩策略，调用 LLM 将对话历史总结为摘要，配合状态重注入机制使用               |
| **AgentContextState**   | Agent 运行时的结构化状态对象，记录拓扑、连接、任务进度等关键信息，用于上下文压缩后的状态重注入 |
| **diminishing_returns** | 收益递减检测，当 Agent 连续多轮循环产出低增量时自动停止，防止无效消耗（P2 实现）      |
